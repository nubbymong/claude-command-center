## Implementation authority

The design's review record lists *Owner approval: Pending* and *Implementation
authority: None*. Gate 0 therefore changes no production code. It adds tests,
evidence and gate scripts only. **No production-code commit is made until the
owner has approved the design and answered the blocking decisions below (D1,
D2, D3, D7, D10, D11).** Decisions that only pick between design-compliant
options (D4, D5, D6, D8, D9, D12) carry a recommendation; the recommendation
is applied only after the owner's go for implementation.

## Decisions required before production refactoring

**Blocking** (the design and the base disagree, or the design reserves the
call for the owner; nothing is assumed):

**D1. Claude realm mechanism (design premise).** The base isolates Claude
accounts by `USERPROFILE`/`HOME` redirection (`withProfileHome`), not
`CLAUDE_CONFIG_DIR`; an existing test asserts that variable is absent.
*Proposal:* implement the Claude realm as the existing profile-home mechanism
and treat the design's variable name as a label. Preserving Claude behaviour
(design principle 10) outranks the literal env-var name.

**D2. macOS Claude multi-account.** Not supported on the base (the login
keychain is located through `$HOME`), gated in three places. Design 15 makes a
platform exclusion an owner-approved, documented one. *Proposal:* WP1 keeps
the exclusion for Claude realms on macOS and records it in the acceptance
evidence; Codex realms are isolated on macOS.

**D3. Launch environment policy.** Design 12 makes an allowlist the authority
for every process WP1 launches. For setup/auth/status/logout subprocesses
that is implemented as written. For the interactive PTY session, a strict
allowlist strips the user's shell environment (PATH, locale, tooling) and
changes Claude behaviour. *Proposal:* managed PTY launches inherit the parent
environment, then the binding-derived realm variable is set last and the
known provider credential variables (`OPENAI_API_KEY`, and `CODEX_HOME` when
it is not the bound realm) are removed, with negative tests (WP1.38). This is
a deviation from the letter of design 12 and needs an explicit ruling.

**D7. Codex CLI versions for the matrix (WP1.64, WP1.71).** The host has
`codex-cli 0.153.4`; the design pins `0.155.1`; npm latest is `0.155.1`. The
design needs a declared *minimum* supported version. *Proposal:* minimum =
`0.153.4`, pinned reference = `0.155.1`, release candidate = npm latest at
qualification time. Claude Code on the host is `2.1.278`.

**D10. Tokenomics and managed Codex realms.** The indexer reads the default
`~/.codex/sessions` only (`tokenomics-service.ts`, ignores `CODEX_HOME`).
Once WP1 creates managed realms, sessions run on them are not indexed until
the observability work package. External-default accounts are unaffected.
*Options:* (a) accept for 2.1.1 with a known-issues entry in the feature
guide and the user guide; (b) pass each active realm's sessions directory
into the indexer in WP1 (widens scope into tokenomics). *Proposal:* (a).

**D11. Deliberate test replacement (WP1.65).** The ledger schedules the
deletion of `stores/codexAccountStore.test.ts`, `providers/codex/auth.test.ts`,
`main/codex-spawn-identity.test.ts` and two `auth.json` fixtures, the
adaptation of twelve Codex-side tests (listed with disposition `replace`) and
five Claude-side tests (`claudeTestChanges`), each with its replacement
coverage named. WP1.65 requires an owner-approved disposition for deliberate
test replacement. *Request:* approve the list as recorded, or strike entries.

**Recommended defaults** (design-compliant either way):

**D4. Where the WP1 issue/premise lives.** Design 18.2 asks for a public-repo
issue; the owner's standing rule routes all tickets to the private planning
repo, which this task must not modify. *Recommended:* the premise assessment
section goes in the PR body; no public issue is filed.

**D5. Linux in the CI test matrix.** The base runs the test matrix on Windows
+ macOS only. *Recommended:* add `ubuntu-latest` to the `test` job matrix in
`ci.yml` as part of the PR (`ci-run` gated like the others).

**D6. Coverage toolchain.** None exists on the base. *Recommended:* add
`@vitest/coverage-v8` as a devDependency and a `test:coverage` script. The
*before* figure must be produced by running that tooling on `6bafcc33` itself
(a throwaway worktree), never on the candidate, or the comparison in design
16.9 is meaningless.

**D8. Resources for real-CLI, packaged and keyring qualification.** These
cannot be produced from the build agent's session alone: disposable
ChatGPT/OpenAI test identities (browser and device flows are manual gates;
the API-key flow needs a short-lived restricted key revoked after the run);
packaged-app smoke on Windows, macOS and Linux outside the checkout; native
keyring smoke under an ephemeral runner identity. Until they are supplied the
PR stays in **draft** and WP1.2, WP1.10, WP1.11, WP1.20, WP1.32, WP1.63,
WP1.64, WP1.71 and WP1.72 remain `planned`, never described as complete.

**D9. Mandated evidence files versus the repo's "no status docs" rule.**
`AGENTS.md` discourages status/summary docs; the design mandates a baseline
record, ledger, traceability manifest and matrix results in or linked from the
PR. *Recommended:* keep them under `docs/wp1/` and `tests/wp1/` as
machine-checked evidence, and say so in the PR body.

**D12. Public-repo sensitivity ruling before push.** `base-delta.md` records
that provider enablement is a renderer-side setting the main process does not
read, and the Codex characterization tests describe the base's API-key IPC
shape. Both are visible in already-public source and are not remote
vulnerabilities; the review lead confirms that reading before the branch is
pushed.
