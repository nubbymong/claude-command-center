## 2026-08-22 -- #379 GUI-subsystem tools bleed their log over the terminal

Windows programs marked `Subsystem = 2` (GUI) in their PE header -- the
Slic3r/wxWidgets family, Inkscape, several Qt tools, parts of Git -- print by
doing `AttachConsole(ATTACH_PARENT_PROCESS)` then `freopen("CONOUT$")`. The
first half attaches to the PARENT's console, so no flag on the child prevents
it; the second half REPLACES the inherited handles, so every redirect we applied
is discarded and the text goes into the console screen buffer the TUI is drawing
into. Owner's measured matrix (2026-08-21, Bambu Studio): every launch captures
0 bytes and most still bleed; only a parent with NO console both suppresses the
bleed and captures the log (5621 bytes).

### What was actually wrong here

Inventoried every place the app starts a user-named executable and classified
the parent. The result was not what the issue's checklist assumed:

- **Main-process spawns were already correct.** Electron main has no console, so
  every `child_process.spawn` from it is fix A by construction, and each site
  that wants output already pipes it (cloud-agent dispatch, the headless
  `claude` runner, the legacy npm install, the Codex probes). The three
  `detached: true` sites (vision browser, sign-in browser, update installer) all
  pair with `stdio: 'ignore'` -- output deliberately discarded -- which is safe.
  Nothing needed changing; `tests/unit/main-spawn-console-audit.test.ts` now
  pins the invariant so a future `detached: true` + pipe cannot slip in.
- **Command buttons were the real exposure, and they do not spawn at all.** A
  button TYPES a line into a live ConPTY (`CommandBar.sendCommand` ->
  `pty.write`). The parent of whatever that line starts is the shell inside that
  pty, and that shell HAS a console -- the pty's. So the tool attaches to it and
  paints over the pane. This is why no spawn flag could ever have fixed it: it
  needed a different PARENT, not different flags.

### What was built

- `src/shared/gui-exe.ts` -- the shared vocabulary, the mechanism and the
  measured matrix written down once.
- `src/main/pe-subsystem.ts` -- reads `Subsystem` at `e_lfanew + 0x5C`.
  Parsing is split from I/O so the tests build headers byte by byte; CI has no
  GUI-subsystem binary and shipping one would be worse. Noted for the next
  reader: that offset is the same for PE32 and PE32+ because PE32+ drops
  `BaseOfData` (-4) and widens `ImageBase` (+4) and the two cancel.
- `src/main/resolve-executable.ts` -- finds the file a typed line would run, by
  walking PATH/PATHEXT with `fs`. Deliberately does NOT spawn `where`: spawning
  to answer "what would this spawn" is the wrong shape on a security-sensitive
  path.
- `src/main/gui-exe-runner.ts` + `ipc/exe-handlers.ts` -- the console-less run.
  Gate: a GUI-subsystem PE image only, at the absolute path we resolved and
  sniffed, argv as an ARRAY, `shell: false`, `detached: false`, capped output /
  duration / concurrency. It grants the renderer no new capability (a button can
  already type an arbitrary line into a live shell, which is strictly more); what
  it adds is a parent with no console.
- Renderer: `GuiExeDialog` warns and offers the choice, `CapturedRunModal` shows
  the log, `CustomCommand.guiExePolicy` remembers the answer per button.

### Fix E, and its honest limit

A tool run in the pty anyway writes straight into the console screen buffer.
Those bytes never pass through the pty stream, so xterm never marks the cells
dirty -- the screen and xterm's model disagree and xterm cannot know. The repair
is an unconditional repaint (`staleGlyphRepainter.settleStrong`), reached from
the command bar through a new per-session `repaintRegistry`.

The limit worth recording: there is no child-exit signal available. The pty's
shell is still alive, only IT knows its child ended, and the bleeding output
never reaches us to re-arm a quiet-window timer. So `scheduleBleedRepaints`
sweeps at 0 / 2 s / 8 s instead of waiting for an event that does not exist. It
also cannot un-draw the log -- only the TUI's next frame does that. This is the
expected-but-ugly case the issue asks to be recorded, not a cure.

### Verification

The issue's 30-second real-exe check cannot run on CI (no Subsystem=2 binary,
and half the result is "did text land on the frame?", which only a human sees).
It is `scripts/verify-console-bleed.mjs`, which reproduces both matrix rows on a
machine that has such a tool, plus an `it.skip` in
`tests/unit/console-bleed-verification.test.ts` documenting how to run it. The
script carries its own plain-ESM copy of the header read (no TS build step under
bare node); a real test asserts the two copies agree, so they cannot drift.

Follow-up not taken: `terminalOptions.command` (a session's own launch line) is
the other user-named-executable surface and is not probed -- it runs once at
spawn, before any terminal exists to warn into.
